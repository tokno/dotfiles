# 文章レビュー

## 使い方

明示的に呼ばれたときに渡された文字列は、自動で起動されたときと同じく依頼文として扱う。

- **対象** … 依頼文で指定されたファイル。指定がなければ、会話に貼り付けられた資料か、会話中で話題になっているファイル、なければ IDE で開いているファイルを対象にする。どれとも決められなければ、推測せずに聞く
- **観点** … `整合` `論理` `段落` `構成` `表現` `読者`。依頼文から読み取る（「論理だけ見て」なら論理のみ）。指定がなければ全観点を実行する（場所ごとの設定で既定を変えられる）

## 自己点検として使うとき

エージェント自身が書いた資料・説明文を、ユーザーや第三者に渡す前に点検するときは次のように進める。

- **対象** … 書き上げた下書き。ファイルでもエージェント自身の出力でもよい
- **観点** … 全観点。段落で構成されない文書（箇条書き中心の説明文など）では、通常どおり観点3を省略する
- **出力** … レポートは出さない。「必須」の指摘は下書きに直接反映し、「任意」はエージェントが判断して反映する。下書きを渡すときに、直した点を3行程度で添える
- 「文書は編集しない」の規則は、ユーザーが書き手の場合に限る。自己点検では書き手はエージェントなので、反映まで行う

## 対象

日本語のテキスト形式の文書のうち、情報を伝えるために書かれた資料・説明文（手順書、提案書、議事録、告知文、README など）を扱う。
会話の文章（チャットのメッセージ、メールの返信など、相手とのやり取りとして書く文章）は、長さにかかわらず対象外。
資料であれば、ファイルでなく会話に貼り付けられたものも対象にする。

## 場所ごとの設定

レビューを始める前に、対象ファイルのフォルダからホームディレクトリまで上へ辿って `CLAUDE.md` を読み（ホームディレクトリ直下のものを含む）、`writing-review` の設定（見出し、または設定ファイルへの参照）を探す。見つかった設定はこのスキルの既定より優先し、近いフォルダの設定ほど優先する。
会話に貼り付けられた資料は、作業ディレクトリを対象のフォルダとして扱う（設定を探す起点にも、既定の参照文書 `README.md` を探す場所にもなる）。

設定できる項目と、設定がないときの既定は次の通り。

| 項目 | 内容 | 既定 |
|---|---|---|
| 参照文書 | 対象と照合するために先に読む文書 | 同じフォルダの `README.md` だけ |
| 対象外 | レビューを断る文書の種類 | テキスト以外、会話の文章 |
| 既定の観点 | 依頼文で観点が指定されなかったときに実行する観点 | 全観点 |
| 追加のチェック項目 | 各観点に足すチェック項目 | なし |
| 態度の補足 | 下の「態度」に加える、その場所固有の判断基準 | なし |

## 事前の準備

対象ファイルは最初から最後まで読む。抜粋で済ませない。

参照文書（設定がなければ同じフォルダの `README.md`）も先に読む。既存ルールとの矛盾や、過去に予告したまま回収されていない約束を見つけるため。ここを飛ばすと、どこにでもある文章術のアドバイスしか出せない。対象ファイルが `README.md` そのものであるときと、`README.md` が存在しないときは読まない。既定で読んだ `README.md` が対象文書と無関係な内容なら、照合には使わず、目的と想定読者の推定にだけ使う。

読み終えたら、観点に入る前に文書の**目的**（何のために書かれたか）と**想定読者**（誰が読むか、前提知識をどこまで共有しているか）を特定する。冗長か、説明が足りないか、必須か任意かは、どれもこの2つを基準に判断するため。文書から読み取れなければ推定し、推定であることを出力に明記する。

## 観点の進め方

以下の観点を、この順に1つずつ行う。順番には意味がある（整合を論理より先に行うのは、値の誤りを残したまま論理を検討しないため）。

---

## 観点1: 整合

文書の中の日付・数値・参照が、文書の中や参照文書と食い違っていないかを確かめる。外部の情報は調べない。

### 手順

1. 日付・曜日・時刻・金額・人数・場所・条番号などの具体的な値と、「第◯条参照」「前述の通り」などの参照をすべて抜き出す
2. 下のチェック項目を当てる
3. 確かめられなかった値（年が書かれていない日付など）は、何を仮定したかを書く

### チェック項目

- **日付と曜日** … 曜日が日付と合っているか。**必ずコマンドで確かめる**（`python3 -c "import datetime; print(datetime.date(2026, 10, 25).strftime('%a'))"` など）。暗算しない。年が書かれていなければ、文書の作成日やフォルダ名から推定する
- **計算** … 合計・内訳・割合・開始と終了の時刻と所要時間が合っているか。これも**必ず計算して確かめる**
- **同じものの値の食い違い** … 日時・場所・金額などが、箇所によって違う値で書かれていないか
- **参照先** … 「第◯条」「前述」「別紙」が実在し、指している内容が合っているか
- **参照文書との食い違い** … 設定で指定された参照文書にある値・表現と矛盾していないか
- **予告の回収** … 文書内で予告・約束したことが、文書内か参照文書で果たされているか（予告した内容が次章の頭に置かれているかという位置の問題は観点4で扱う）

主張どうしの矛盾は観点2（論理）で扱う。この観点で扱うのは値と参照の食い違い。

---

## 観点2: 論理

ロジックツリーを組んでから判定する。読み流しでは破綻は見つからない。

### 手順

1. 文書から次の4種類を抽出する
   - **事実・前提** … 検証可能な記述
   - **目標** … 達成したいこと
   - **条件** … 目標に必要なこと
   - **手段** … 条件を満たす方法
2. 依存関係をツリーに組み、コードブロックで出力する
3. 下のチェック項目を順に当てる

### チェック項目

- **根拠のない主張** … 前提から導けない結論がないか
- **孤立した枝** … どの目標・条件にも繋がらない記述がないか
- **相互矛盾** … 離れた場所で反対のことを述べていないか
- **結論の重複導出** … 同じ結論を別々の場所で二度導いていないか
- **飛躍** … AとBの間に省略された前提がないか

ツリーは必ず出力する。書き手が自分で構造を確認できるようにするため。

---

## 観点3: 段落

段落で構成されていない文書（条文、箇条書き中心のメモなど）では、この観点を省略し、省略した理由を1行書く。

### 手順

1. 空行で区切って段落を列挙する
2. 各段落について判定する
   - 先頭の文が主張になっているか（予告や前置きではないか）
   - 1段落に主張が1つか
   - 2文目以降がすべて先頭文を支えているか
3. **各段落の先頭文だけを順に並べて読む。** それだけで文書の筋が通れば合格

### よく出る崩れ

- 先頭が「〜について説明します」「1点補足です」のような予告だけで、中身がない
- 重要な主張が2文目以降に埋もれている（文書の転換点がここに隠れやすい）
- 主張とその理由が別々の段落に分かれている
- 1つの主張を支える根拠が、段落をまたいで散らばっている

手順3の通読テストは必ず実施する。合格しているなら、合格していると明記する。

---

## 観点4: 構成

### 手順

1. 見出しをすべて抜き出す
2. 各章の実際の内容を1文で要約する
3. 見出しと要約を突き合わせる

### チェック項目

- **見出しと中身のずれ** … 見出しが「〜の難しさ」なのに中身は要件の列挙、など。分量の多い方が実態
- **章の接続** … 章末と次章の冒頭が繋がるか。予告した内容が次章の頭にあるか
- **重複** … 同じ予告・同じ挨拶が2箇所にないか（同じ結論を二度導いている場合は観点2で扱う）
- **順序** … 結論を先に置いた場合、その理由が遠すぎないか
- **番号体系の衝突** … 別の意味の「1. 2. 3.」が近接していないか

---

## 観点5: 表現

### 手順

1. 文を1つずつ読み、下のチェック項目を当てる
2. 表記ゆれの候補を見つけたら、**必ず grep で全出現を数える。** 目視で1件見つけて報告するのは不十分。何箇所あるかを示し、どちらに統一するかを書き手に選ばせる

### チェック項目

- **係り受けのねじれ** … 修飾節の主体が文中にあるか
- **一文二主張** … 1文に独立した主張が2つ入っていないか
- **指示語の受け先** … 「も」「後者」「これ」「そのため」が何を指すか辿れるか
- **表記ゆれ** … 同義語の混在、送り仮名、漢字/ひらがな
- **冗長** … なくても通じる語句や修飾、隣り合う文での同じ内容の言い直し
- **誤読** … 別の意味に取れる語がないか

---

## 観点6: 読者

### 手順

1. 事前の準備で特定した目的と想定読者を確かめる
2. 想定読者の立場で、文書を最初から通して読む
3. 下のチェック項目を当てる

### チェック項目

- **目的の達成** … 文書全体として目的が達成されているか
- **読者への届き方** … 想定読者の前提知識で読み通せるか。想定読者が、自分宛ての文書だと分かるか
- **固有名詞のリスク** … 個人・団体への言及が、文書が転送されたときに問題にならないか

---

## 出力

レポートは必ず下のテンプレートの形で出す。`< >` の部分を埋める。「総評」から「指摘」までの見出しは毎回同じものを同じ順に置き、該当がない欄も消さずに「なし」と書く。「観点ごとの記録」だけは、実行した観点の分だけを置く。

````markdown
# レビュー: <ファイル名>

- 設定: <読んだ設定ファイル。なければ「なし（既定で実行）」>
- 参照文書: <実際に読んだ文書。なければ「なし」>
- 観点: <実行した観点>（<省略した観点>は省略: <理由>）
- 目的: <この文書が達成したいこと>
- 想定読者: <誰が読むか。推定なら「（推定）」を付ける>

## 総評

<1〜2文。配布・提出できる状態かどうかを言い切る。問題がなければ「完成しています」>

## 良い点

- [L<行>](<パス>#L<行>) <何がどう良いか。「良いです」だけで終わらせない>

## 指摘

### 必須

#### 1. <問題の短い要約>（<観点名>）[L<行>](<パス>#L<行>)

- 問題: <何が問題か>
- 理由: <なぜ問題か。読者にどう影響するか>
- 現在:
  > <該当箇所の原文>
- 修正案:
  > <そのまま差し替えられる文>

### 任意

#### 2. <問題の短い要約>（<観点名>）[L<行>](<パス>#L<行>)

<必須と同じ形式>

## 観点ごとの記録

### 整合
- 確かめた値: <種類ごとの件数>
- 仮定: <確かめられず仮定したこと>

### 論理
```
<ロジックツリー>
```

### 段落
- 先頭文の通読テスト: <合格 / 不合格>（<不合格なら筋が切れる箇所>）

### 構成
| 見出し | 実際の内容（1文） |
|---|---|

### 表現
| 表記 | 件数 |
|---|---|

### 読者
- 目的の達成: <達成 / 未達>（<未達なら何が足りないか>）
````

- **必須と任意**は次の基準で分ける。必須は、直さないと配布・提出できないもの（値の誤り、論理の破綻、読者の誤読を招くもの）。任意は、それ以外
- **位置の示し方**は、ファイルなら `[L<行>](<パス>#L<行>)` の行リンクにする。会話に貼り付けられた資料には行番号がないので、代わりに該当箇所の冒頭を「」で引用する（例:「次回の会議は〜」）
- **指摘の番号**は「必須」から「任意」まで通しで振る。「2と4を直して」と指定できるようにするため
- **指摘の並び**は、必須・任意それぞれの中で重要度順にする
- **指摘の見出し**は「番号. 要約（観点名）行番号リンク」の形を崩さない。見出しだけ追えば全体が分かるようにするため
- **観点ごとの記録**に省略した観点を置かないのは、冒頭の「観点」の行で省略の理由を示しているため

（自己点検の場合は上の「自己点検として使うとき」に従う）レポートを出したら終える。文書は編集せず、「適用しますか」とも聞かない。どの指摘をどう採り入れるかは書き手が決め、編集はレビューとは別の依頼として、その場所のルールに従って行う。

## 態度

- **断定する。** 判断を求められて「〜という考え方もあります」で逃げない
- **理由を構造で説明する。** 「この段落は手順を説明しているので時系列順、次の段落は選択肢を比べているので重要度順に並べる」のように、なぜそうなるのかの仕組みを示す
- **前言の撤回を厭わない。** 問いの立て方を取り違えていたと気づいたら、その場で言い直す
- **書き手の判断には従う。** 反対意見は理由とともに一度述べる。決定が変わらなければ、その決定を前提にレビューを続ける
- **足すべきでないものは足さない。** 文書を弱くする追加は、修正案として出さない
